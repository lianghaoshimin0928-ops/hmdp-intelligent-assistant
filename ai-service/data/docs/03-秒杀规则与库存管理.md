# 秒杀规则与库存管理

## 一人一单规则

同一用户对同一张秒杀券**只能下一单**。重复下单时接口会返回「不能重复下单」。

这个限制由两层机制共同保证：

1. **Redis 层**：用 Set 结构记录已下单用户，下单前先判断是否存在。这是第一道防线，能挡掉绝大多数重复请求。
2. **数据库层**：订单表上建有 `(user_id, voucher_id)` 唯一索引。即使 Redis 判断被绕过，数据库插入也会失败，作为最终兜底。

之所以要两层，是因为 Redis 可能因主从切换、缓存失效等原因出现判断偏差，数据库唯一索引是最后一道保险。

## 库存扣减的原子性

秒杀最怕超卖。库存判断、库存扣减、记录下单用户这三步必须原子完成，否则并发下会出现「库存显示有，实际卖出去更多」。

平台的做法是把这三步写进一段 **Lua 脚本**，交给 Redis 单线程执行。Lua 脚本在 Redis 内部是原子执行的，中间不会被打断，因此不会出现两个请求同时判断库存都成功、结果扣成负数的情况。

## 秒杀券的活动时间窗口

每张秒杀券有 `begin_time` 和 `end_time` 两个字段，构成活动时间窗口。请求时间不在窗口内时，接口直接拒绝。

以 103 茶餐厅的 100 元秒杀券为例：活动时间从 2026-11-10 00:00:00 开始，到 2026-12-31 23:59:59 结束，库存 97 张。

## 常见失败原因

抢券失败通常有以下几种原因，接口会返回对应提示：

- **库存不足**：券已抢完
- **不能重复下单**：该用户此前已抢过这张券
- **活动未开始或已结束**：不在时间窗口内
- **优惠券不存在**：voucher_id 传入错误

## 异步下单

为了削峰，秒杀请求在 Redis 中校验并扣减库存成功后，并不直接在数据库落单，而是把下单任务投递到消息队列，由消费者线程异步创建订单。

这样做的收益是：接口响应时间从「等数据库事务」降到「等一次 Redis 写入」，数据库写入压力被消费者线程平滑吸收，峰值不会打垮数据库。
