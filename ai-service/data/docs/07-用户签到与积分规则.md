# 用户签到与积分规则

## 签到机制

用户每天可以签到一次，签到后获得积分奖励。

签到数据用 Redis 的 **BitMap** 存储，key 为 `sign:{用户id}:{年月}`，例如 `sign:2:202611`。一个月最多 31 天，BitMap 只需要 31 个 bit，占用空间不到 4 字节。

如果换成用数据库记录每次签到，一个用户一个月就是 31 行，一年 372 行，百万用户就是数亿行。BitMap 把这个开销压到了几乎为零，这是选择 BitMap 的核心理由。

## 连续签到天数怎么算

签到位图按天偏移，第 1 天对应 offset 0，第 2 天对应 offset 1，以此类推。

计算连续签到天数时，从今天对应的 bit 往前逐个检查，遇到第一个为 0 的 bit 就停止，累计的位数即为连续天数。这个操作的复杂度与连续天数成正比，通常很小。

## 本月签到次数

直接用位图的位计数（BITCOUNT）即可得到本月已签到天数，O(N) 但 N 只有 31。

## 积分规则

- 每日签到：固定积分
- 连续签到：连续天数越多，单日奖励越高，具体档位由运营配置
- 积分可在下单时抵扣，抵扣比例由平台统一配置

积分与签到数据是两套存储：签到用 BitMap 追求极致省空间，积分需要精确累加和流水查询，因此存在数据库。

## 常见的统计需求

平台还会用 BitMap 和 HyperLogLog 处理两类统计：

- **用户签到分析**：BitMap，支持按位与计算「本周签到几天」
- **独立访客数（UV）统计**：HyperLogLog，用 12KB 内存估算亿级 UV，标准误差约 0.81%

UV 统计之所以不用 Set，是因为 Set 要存全量用户 id，内存随用户数线性增长；HyperLogLog 是概率数据结构，只保证估算精度，能换来内存的常数级占用。牺牲精度换空间，在「只需要看趋势」的场景下是划算的。
