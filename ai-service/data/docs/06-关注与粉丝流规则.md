# 关注与粉丝流规则

## 关注关系

用户可以关注其他用户，也可以随时取消关注。关注关系用 Redis Set 存储，key 为 `follows:{用户id}`，member 是被关注用户的 id。

用 Set 而不是列表，是因为需要高频判断「我是否关注了某人」，Set 的成员判断是 O(1)。

## 共同关注

查看他人主页时，平台会展示「你和 TA 的共同关注」。实现方式是对两个用户的关注 Set 做交集运算（SINTER），结果即为共同关注的用户列表。

这也是选择 Set 的核心原因之一：交集运算是 Set 的原生能力，换成数据库需要 JOIN，成本高得多。

## 粉丝流（Feed 流）

用户关注的人发布新笔记时，笔记要出现在粉丝的信息流里。业界有两种基本方案：

- **推模式（写扩散）**：作者发布笔记时，立刻把笔记 id 写入所有粉丝的收件箱。读的时候直接读自己的收件箱，**读快写慢**。适合粉丝量不大的普通用户。
- **拉模式（读扩散）**：发布时只存一份，读的时候去聚合所有关注对象的笔记。写快读慢。适合粉丝量巨大的大 V。

平台采用**推模式**，收件箱用 Redis ZSet 存储，key 为 `feed:{用户id}`，member 是笔记 id，score 是发布时间戳。

## 滚动分页

粉丝流用滚动分页而不是传统的页码分页。原因有两个：

1. 信息流实时更新，用页码会出现「翻到第 2 页时第 1 页的内容已经变了」的重复或遗漏问题。
2. 用发布时间戳作为游标，天然支持「从这里往下看」。

具体做法是以上一页最后一条的时间戳作为下一次查询的最大值，做逆序范围查询。由于多条笔记可能时间戳完全相同，还必须配合偏移量跳过已读部分，否则会重复返回同一条。

## 大 V 的特殊处理

如果严格用推模式，一个百万粉丝的账号发一篇笔记就要写一百万次，不可接受。实际工程中通常做混合策略：普通用户走推模式，粉丝超过阈值的账号走拉模式，读取时把两种来源合并。
