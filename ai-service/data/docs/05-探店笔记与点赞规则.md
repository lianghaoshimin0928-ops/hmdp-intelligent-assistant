# 探店笔记与点赞规则

## 什么是探店笔记

探店笔记是用户对商户发布的图文内容，包含标题、正文、图片和关联的商户 id。笔记是平台的主要 UGC 内容来源，也是用户发现新商户的重要入口。

一篇笔记只关联一家商户。用户在笔记详情页可以直接跳转到对应商户页并领取优惠券。

## 点赞机制

每个用户对每篇笔记只能点一次赞，可以取消点赞。点赞数据有两层：

1. **Redis ZSet**：key 为 `blog:liked:{笔记id}`，member 是用户 id，score 是点赞时间戳。用 ZSet 而不是 Set，是因为要同时满足三个需求：判断是否点过赞、按时间倒序排榜、统计点赞总数。
2. **数据库明细表**：记录用户与笔记的点赞关系，用 `(笔记id, 用户id)` 唯一索引防重。

## 点赞排行榜

笔记详情页下方的点赞榜展示**最近点赞的前 5 名用户**，按点赞时间倒序。实现方式是对 ZSet 做逆序范围查询，取前 5 个 member。

判断当前用户是否点赞过，用 ZSet 的分数查询即可，不需要额外查数据库。

## 为什么要异步落库

热门笔记在短时间内可能收到大量点赞。如果每个点赞请求都同步写两次数据库（一次插明细、一次更新计数），数据库会成为瓶颈。

平台的做法是点赞请求只写 Redis 并投递一条异步消息，由消费线程批量落库。计数以 Redis 的基数统计为准，数据库只做持久化和对账，因此允许秒级的最终一致。

## 大 key 风险

单篇爆款笔记的点赞 ZSet 可能有上百万元素，这属于典型的**大 key**。大 key 的危害是：读取时阻塞 Redis 单线程、删除时造成明显卡顿、集群下数据倾斜。

常见的处理方向是：按时间分片存多个 ZSet、对超大 key 做容量上限并降级为采样统计、用 SCAN 代替 KEYS 遍历。
